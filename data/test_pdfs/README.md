# Test PDFs for the document agent

Generated by `scripts/generate_test_pdfs.py`. One baseline claim
(`baseline_claim.json`, `CLM-DOCTEST-001`, estimated_amount $23,100), with 7
cases that each change exactly one document from a clean 3-document set -
everything else held fixed, same "change one thing, compare" discipline as
the golden-set fairness pairs.

These are manual-test fixtures for the document agent (not yet built), not a
pytest-covered dataset. Use them as a checklist once extraction + the
arithmetic/plausibility/classification checks exist.

| File(s) | Case | Expected document-agent behavior |
|---|---|---|
| `case1_clean_police_report.pdf`, `case1_clean_other_driver_info.pdf`, `case1_clean_repair_estimate.pdf` | Clean baseline | All 3 extract cleanly into their matching schema (`PoliceReportFields`/`OtherDriverInfoFields`/`RepairEstimateFields`). `line_items_sum` == `stated_total` == claim's `estimated_amount` ($23,100). No flags. |
| `case2_scanned_repair_estimate.pdf` | Scanned/image-only PDF (no text layer) | Same content as case 1's repair estimate, rendered as a flat image. Tests Docling's OCR fallback - should still extract the same fields as case 1. If OCR isn't wired in yet, this is expected to produce a mostly-empty extraction (no text layer to read directly). |
| `case3_arithmetic_mismatch_repair_estimate.pdf` | Arithmetic mismatch | Line items sum to $23,100 but the printed total says $28,500. Tests the `line_items_sum` vs `stated_total` code check - should produce a `document_verification_flags` entry, data kept (not nulled). |
| (reuse `case1_clean_repair_estimate.pdf`) | Wrong document in wrong slot | Upload case 1's repair-estimate PDF into the **police_report** slot during testing. Tests classify-then-extract mismatch detection - should flag "wrong document type uploaded" and treat the slot as not fulfilled (same as missing). |
| `case5_corrupt.pdf` | Corrupt/unreadable file | Not a valid PDF (truncated garbage bytes with a `.pdf` extension). Tests the Docling-throws fallback - field should stay `None`, a flag recorded ("could not be parsed"), pipeline must not crash. |
| `case6_plausibility_mismatch_repair_estimate.pdf` | Plausibility mismatch | Internally consistent ($85,000 line items sum to $85,000 stated total) but wildly higher than the claim's own `estimated_amount` ($23,100). Tests the cross-field plausibility check - distinct from case 3's internal-arithmetic check. Should flag, not reject. |
| `case7_sparse_repair_estimate.pdf` | Legitimately sparse (lump-sum) | No itemized line items, just a lump-sum total. Per `RepairEstimateFields`' own documented semantics, an empty `line_items` list means "confirmed zero itemized lines," not "unchecked." Should extract cleanly with `line_items=[]`, `stated_total=$23,100` - must NOT be flagged as a verification failure.
