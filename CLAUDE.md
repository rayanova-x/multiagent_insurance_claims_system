# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Multi-agent insurance claims processor using **LangGraph** (orchestration) + **CrewAI** (fraud sub-crew). FastAPI backend, React+Vite frontend, SQLite persistence. Two LLM providers (Gemini, Groq) and two country profiles (US, India) switchable at runtime.

## Architecture

### Pipeline (src/agents/graph.py)

LangGraph `StateGraph`. Every agent node is wrapped in `guard_node()` (budget checks before, token/cost/time accounting after). Execution paths:

- **Path A** (normal): intake -> fan-out [damage_assessor, policy_checker, fraud_crew] (parallel, mutually isolated - see "Fan-out + consistency coordinator" below) -> `fan_out_join` -> consistency_coordinator -> settlement -> evaluator -> communication
- **Path B** (HITL): pauses at `hitl_checkpoint` on a confirmed-fraud/property trigger, a confidence gate, or an unresolved MATERIAL consistency conflict at its retry cap; approved -> resumes at the correct next step. Also pauses after the evaluator when the quality gate fails or the amount is at or above the country's `hitl.triggers.min_amount` (settlement sign-off).
- **Path C** (auto-reject): fan-out -> `fan_out_join` -> auto_reject -> communication, when fraud_crew's recommendation is CONFIRMED (checked in `route_after_fan_out`, before the consistency coordinator even runs - a confirmed-fraud claim never needs cross-branch consistency checking). `route_after_fan_out`'s conditional edge is attached to `fan_out_join` alone (a genuine single join point all three branches feed via plain edges), never to each branch separately - a real bug once had it wired per-branch, causing three independent routing opinions to all fire instead of one shared decision; see the scenario-test rebuild-status entry below.
- **Path D** (intake failure): intake -> communication (invalid claim)
- **Path E** (fast mode): intake -> settlement -> evaluator -> communication (amount < `pipeline.fast_mode.max_amount`)

A guardrail halt (calls, tokens, cost or active-time budget) sends the claim from any router to `hitl_checkpoint`, then to communication with a template letter.

Per-agent **confidence gates** (fraud/damage/policy, risk-stratified by claim amount) and **property-based triggers** (fraud score threshold, physical-inspection flag, policy exclusions/compliance flags) all live in `route_after_consistency_check` now, not `route_after_fan_out` - they run AFTER the consistency coordinator's own retry loop has had a chance to resolve a conflict, so a human reviewer never sees a gate fire on a branch output that a same-pass retry would have corrected.

#### Fan-out + consistency coordinator

`damage_assessor`, `policy_checker`, and `fraud_crew` run as three parallel, **mutually isolated** branches - none reads another's output, by design (see "Design principles" below, and the fan-out rebuild-status entry, for why isolation is the point, not a gap). Once all three join, `consistency_coordinator` (`src/agents/consistency_coordinator.py`) is the only place that sees all three outputs together. It checks for exactly 2 cross-branch conflict types (`ConflictType` in `src/models/schemas.py`):

- `MISSED_FACT` - a detail one branch's notes surfaced that another branch's judgment never got to weigh (e.g. damage_assessor notes commercial markings or racing modifications that policy_checker's exclusion judgment didn't see).
- `SEVERITY_MISMATCH` - two branches' read of the incident's severity disagree in a way that could change the payout or coverage decision (e.g. damage_assessor says total_loss while fraud_crew's narrative-consistency read describes "minor damage").

A third candidate, repair-cost-to-narrative plausibility, was deliberately **dropped**: `damage_assessor` already receives both the incident description and repair line items in the same prompt call, and its own hard-coded Rule 3 (40% deviation cap) already checks exactly that - a dedicated cross-branch conflict type would be redundant, not extra precaution.

Each conflict carries a `ConflictSeverity` (`MATERIAL` or `NOTABLE`, tied to real consequence - could this change the payout/coverage/fraud classification - never to how different two texts merely sound) and a `retry_target` (`damage_assessor` or `policy_checker` only - `fraud_crew` is out of scope for retries, consistent with fraud detection being out of scope for this rebuild entirely). Code, not the LLM, decides what happens next (`route_after_consistency_check` + `prepare_consistency_retry_node` in `graph.py`):

- No conflicts, or only NOTABLE ones -> straight to settlement. NOTABLE conflicts never trigger a retry.
- A MATERIAL conflict, target agent still under `agents.consistency_coordinator.max_retries` (default 2, in `configs/base.yaml`) -> `prepare_consistency_retry_node` builds a context string (the conflict's description + reasoning) and routes back to the target agent for one more pass with that added context (`consistency_retry_context` in `ClaimsState`, read by both `damage_assessor.py` and `policy_checker.py`'s prompt-building code, cleared after each read). This repeats until resolved or the cap is hit.
- A MATERIAL conflict at its retry cap -> forced to `hitl_checkpoint` regardless of resolution. The loop is always bounded, same as every other evaluator-optimizer pattern in this codebase.

`consistency_coordinator` fails OPEN (`has_conflicts=False`) on an LLM error, unlike `injection_check`'s fail-closed - there's no safety concern in skipping one run's consistency opinion.

HITL uses LangGraph's `interrupt()` / `Command(resume=...)` with `SqliteSaver` checkpointer for durable pause/resume across restarts. On resume LangGraph re-runs the HITL node from its first line; `enqueue_claim(..., idempotency_key=...)` keeps that from opening a second ticket. Keep every side effect before `interrupt()` idempotent.

### Configuration Hierarchy (src/config.py)

Precedence: runtime override > `.env` > country YAML (`configs/countries/{code}.yaml`) > base YAML (`configs/base.yaml`). Provider and country are set in `.env` only; model IDs and tunables live in YAML.

### Key Layers

| Layer | Location | Purpose |
|---|---|---|
| API | `api/` | FastAPI routes, SQLModel DB, JWT auth, role guards |
| Agents | `src/agents/` | Each agent is a function taking `ClaimsState`, returning a dict update |
| State | `src/models/state.py` | `ClaimsState` TypedDict - the single state object flowing through the graph |
| HITL | `src/hitl/` | `queue.py` (SQLite ticket queue), `checkpoint.py` (trigger rules + priority scoring) |
| Memory | `src/memory/` | ChromaDB + HuggingFace embeddings for similar-claim retrieval |
| LLM | `src/llm.py` | Provider factory - creates LangChain ChatGoogleGenerativeAI or ChatGroq with token tracking callback |
| Guardrails | `src/guardrails/manager.py` | `guard_node()` wraps every agent: per-claim caps on agent calls, tokens, cost, active time; usage carried in state |
| PII | `src/security/pii_masker.py` | Country-aware regex masking; every prompt reads `state["masked_claim"]`, never the raw claim |
| Tools | `src/tools/` | Fraud patterns, policy lookup, memory `@tool`s, `tool_loop.py` (bounded model-driven tool calling used by settlement) |
| Frontend | `frontend/` | React + Vite + Zustand + MUI; proxies `/api` to backend on port 8000 |

### Data Storage

All SQLite databases live in `data/`: `api.db` (users/claims/appeals), `hitl_queue.db` (review tickets), `claims_checkpoints.db` (LangGraph checkpointer). Sample claims for all 5 paths in `data/sample_claims/`.

### Adding a New Country

Create `configs/countries/{code}.yaml` following the structure in `configs/countries/us.yaml`. The config loader auto-discovers it. Also extend `src/tools/fraud_patterns.py`: its patterns and baselines branch on `country.code` ("IN" for India, anything else falls back to US).

## Rebuild status and ground rules

This repo was cloned from `genieincodebottle/aiml-companion` as a reference/starting point for a rebuild happening module-by-module (see sibling project `D:\insurance_agent\casefile` for the predecessor system). Do not assume the code as cloned is the target end state — treat the sections above as "what the original repo does," not as settled decisions for this rebuild.

**Process**: go through the system one module at a time (config → data/state → security → agents → graph/HITL → guardrails → memory → API → frontend). For each module: explain what it does and why in plain language, get an explicit decision (keep / change / cut), make the edit, then verify nothing broke. Don't silently adopt the original repo's design — surface real tradeoffs and let the decision be made explicitly, even when the "obvious" answer seems right.

**Decisions already locked in (do not re-litigate without being asked):**
- **Country scope**: US only for now. `COUNTRY=us` in `.env`. India's YAML profile and the country-switching mechanism stay in the codebase for later but are not being validated or built out.
- **State object**: `ClaimsState` stays a `TypedDict`, NOT converted to Pydantic. A conversion was planned and then tested directly against this repo's installed LangGraph (1.2.16): a Pydantic `BaseModel` state schema does not actually get validated on node-merge — a deliberately wrong-typed field in a node's partial-dict return passed through untouched into the final result, while constructing the same model directly correctly raised. So the conversion wouldn't have delivered the "catch mistakes immediately" behavior it was meant for — it would only look stricter without being stricter. Real validation already exists where it matters: every agent's structured LLM output (`IntakeValidationOutput`, `FraudAssessmentOutput`, etc.) is a real Pydantic model enforced at the LLM-call boundary. Do not re-attempt this conversion without re-testing LangGraph's merge behavior first, and check the project memory (`project-smart-claims-state-model`) before repeating this investigation.
- **LLM outages always reach a human, regardless of amount**: when `src/agents/intake_agent.py`'s LLM call fails (both primary and fallback model exhausted retries — see `src/llm.py`'s multi-layer resilience stack), that's a system failure, not a confidence judgment call, so it's exempt from the amount-based confidence gate. The intake agent already set `confidence=0.40` and appended `"LLM error - requires manual review"` to `validation_flags` on this path; `src/hitl/checkpoint.py`'s Trigger 6 now surfaces that specific flag as its own named trigger ("Intake LLM unavailable...") rather than folding it into the generic flags list, so a reviewer understands immediately why the ticket exists. This was already property-based (flag presence, not confidence) and worked correctly before and after the confidence-gating rework — only the trigger wording changed for clarity.
- **`requires_physical_inspection` is now a real HITL trigger**: it was a write-only field (set by `src/agents/damage_assessor.py`, including unconditionally on its LLM-failure fallback, but nothing ever read it). `route_after_damage` in `src/agents/graph.py` now routes straight to `hitl_checkpoint` whenever it's `True`, regardless of confidence or claim amount — property-based, not confidence-based, since it means the assessor cannot judge the damage from documents alone. `src/hitl/checkpoint.py`'s Trigger 9 surfaces it by name in the review brief when the claim is already pausing for another reason too.
- **`exclusions_triggered`/`compliance_flags` on the policy check are now real HITL triggers too** (same bug pattern, same fix): both were write-only, only ever shown as text to the evaluator/judge, never read to route anywhere. `route_after_policy` now routes to `hitl_checkpoint` whenever either is non-empty — regardless of confidence or claim amount — since a genuine policy exclusion or compliance finding is a concrete, specific problem (and this also catches `policy_checker`'s LLM-outage marker, appended to `compliance_flags` on its failure fallback). See `src/hitl/checkpoint.py` Trigger 10. This was a deliberate choice over a narrower "just fix the outage case" option — the user decided a real exclusion/compliance concern is too important to let through unexamined, accepting more claims may pause as a result.
- **High fraud score (≥0.80) now denies in code at settlement, not just via a prompt instruction**: `src/agents/settlement_calculator.py`'s prompt rule 6 ("if fraud score >= 0.80, decision should be DENIED") was the one hard rule in that file never re-checked after the LLM responded — every other numeric rule there (max payout multiplier, deductible, coverage limit) was already capped in code. The gap was reachable: a claim with fraud score ≥0.45 pauses at the fraud HITL checkpoint, but if a human reviewer approves it anyway, it proceeds to settlement still carrying a fraud score that could be ≥0.80 (auto-reject only fires at ≥0.75 AND narrative risk ≥0.90 AND an explicit admission, so plenty of ≥0.80 claims never auto-reject). Now: if `fraud_output.fraud_score >= 0.80` and the LLM's decision isn't DENIED, code overrides to DENIED — unless a human already explicitly approved the claim (`human_decision in ("approved", "approved_partial")`), which is respected as the one exception, same symmetric-guard pattern as the existing human-override logic in this file.
- **Intake agent redesigned: `is_valid` is now code-computed, not an LLM decision.** The old design had the LLM decide `is_valid` from a prompt stating an explicit, fully deterministic rule ("valid if policy_active AND covered") — the LLM was being asked to restate `True and True = True`, not exercise real judgment; the LLM-failure fallback already proved this by computing the exact same result in one line of code. Now: `is_valid`/`policy_active`/`claimant_eligible` are computed in code before any LLM call, and overwritten after the LLM call regardless of what it returns (same "code wins" pattern as `settlement_calculator`'s caps). `IntakeValidationOutput.confidence` was removed from the schema entirely — there's no genuine uncertainty left to report once the decision is deterministic. The LLM's only remaining job is writing `intake_notes`.
- **New: prompt-injection detection, as a separate, narrow, schema-enforced classifier** (`src/security/injection_check.py`, `check_for_injection()`), gating intake's notes-writing LLM call — NOT folded into intake's main judgment as a vague "is this suspicious" field, since (a) that would duplicate fraud_crew's narrative-consistency job, (b) explicit criteria beats a vague qualifier. Criteria is narrow and explicit, with positive AND negative few-shot examples baked into the Pydantic field description: an injection attempt is an imperative instruction directed at an AI/reviewer/approval process ("approve this immediately", "ignore the policy exclusions") — NOT an ordinary claimant plea or urgency ("I hope this gets approved quickly" is explicitly NOT an injection attempt, to avoid flagging normal human emotion). Defense-in-depth per CLAUDE.md's own "Prompt injection defense" principle: (1) delimited — the text is wrapped in `<claimant_data>` tags with explicit data-not-instructions framing; (2) classified by a dedicated call, not the main reasoning agent; (3) restricted — on detection, intake skips its own notes-writing LLM call entirely and `route_after_intake` forces mandatory human review via `hitl_checkpoint`, regardless of claim amount (property-based trigger, same pattern as `requires_physical_inspection`/`exclusions_triggered` from earlier this session) — per the source guidance, an injection must not be able to "complete an irreversible act alone." If the classifier's own LLM call fails, it fails toward caution (`contains_injection_attempt=True`, forces review) rather than failing open.
- **Damage assessor fully redesigned with explicit company methodology, real few-shot examples, and 4 code-enforced hard rules** (2026-10-19): the system prompt now states the company's actual depreciation table and 75% total-loss threshold explicitly, with two worked few-shot examples built from real claims in `data/stratified_claims/` (CLM-STRAT-043, a repair case; CLM-STRAT-001, a total-loss case) - both deliberately chosen because the claimant's own description text DISAGREES with the computed ratio, to teach the model to trust the math over descriptive language. Four rules are code-enforced after every LLM call via `_enforce_hard_rules()`, never left to the prompt alone (grounded in real insurance practice - total-loss thresholds are a regulatory/compliance line per web research, not adjuster discretion): (1) `should_total_loss()`'s computed ratio forces `repair_vs_replace`, overriding the LLM if it disagrees; (2) `repair_vs_replace=="total_loss"` forces `assessed_damage_usd` to the computed ACV, never a repair-cost figure; (3) a repair assessment deviating more than 40% from the repair-estimate document's real `stated_total` is capped back - the LLM's job is to flag a specific implausible line item, not invent a replacement figure; (4) no repair-estimate document at all forces `requires_physical_inspection=True`, structurally. See `tests/test_damage_assessor.py` (18 tests, including rule-interaction cases).
- **The original "rule 3" (clip outliers against a looked-up typical-cost range) was retired before it shipped, replaced by the real design above.** `get_repair_estimate_range()` (`src/tools/damage_calculator.py`) was a hardcoded table of 10 UNSOURCED cost ranges matched to free text by fragile keyword search - there is no real external database of typical repair costs accessible to this system (checked: the real industry tools, Mitchell/CCC ONE/Audatex, are paid/contract-based). A plausible-looking invented number is not better grounding than letting the model invent one directly - it just hides the fabrication one layer deeper (CLAUDE.md "schema validity is not correctness"). The real fix grounds the assessment in the repair-estimate DOCUMENT's own real, claim-specific line items instead (via the new `ClaimsState.claim_documents` wiring from bug #4 below) - rule 3 above caps deviation from that real number, and rule 4 forces physical inspection when no such document exists at all, rather than guessing from either a lookup table or keywords. `get_repair_estimate_range()` and its backing tables were deleted entirely, not deprecated in place.
- **Bug found via live-testing the repair-cost-grounding redesign (2026-10-19): Decimal fields silently become strings across a JSON round-trip.** `RepairLineItem.amount` is typed `Decimal` (`src/models/documents.py`) so Pydantic's `model_dump_json()` serializes it as a JSON string (Decimal has no native JSON type) - the generated `data/stratified_claims/*_documents.json` files on disk therefore have `"amount": "8100.00"` (a string), and reading them back with plain `json.load()` deserializes that as a Python `str`, not a numeric type. `_repair_estimate_line_items()` in `damage_assessor.py` was formatting `item['amount']` with `:,.2f`, which only works on numbers - crashed immediately on the first live run with `ValueError: Unknown format code 'f' for object of type 'str'`. Fixed at the source: `_repair_estimate_line_items()` now rebuilds each item with `float(item["amount"])` before returning, so every downstream consumer gets a numeric type regardless of how the document data arrived (JSON round-trip or otherwise) - not a one-off patch on the single f-string that happened to crash first. Re-verified live after the fix: all 3 cases (repair-with-document, total-loss-with-document, repair-without-document) matched expectations exactly, including rule 4 correctly forcing `requires_physical_inspection=True` on the no-document case.
- **Found and fixed 4 real bugs while building the above, none of which were the original ask**: (1) `calculate_vehicle_acv` (`src/tools/damage_calculator.py`) double-counted vehicle age - any car over 10 years old fell into one flat base bracket, then had depreciation re-applied on top for every year past 10, so an 11-year-old and a 30-year-old car converged to nearly the same near-zero ACV. Fixed with age-scaled brackets through 30+ years and a sane value floor ($500 US / ₹25,000 India) so compounding can't drive old vehicles to near-zero. See `tests/test_damage_calculator.py`. (2) Our dataset generator shifted `incident_date` forward +11 years but left `vehicle_year` at the real dataset's original value, breaking the real, internally-consistent relationship between vehicle age and claim size - fixed by shifting `vehicle_year` by the same amount (`_shift_year` in `src/data/generate.py`). (3) The other driver's synthetic vehicle year was hardcoded to a stale `2015 + (h % 9)` range in `src/data/claim_facts.py` - fixed to be relative to the actual incident year. (4) **The one the live test actually caught**: `should_total_loss()`/`apply_depreciation()` were computed against `claim.estimated_amount` (the claimant's SELF-REPORTED TOTAL claim figure, which can include injury/property/liability costs, not just vehicle damage) instead of the real vehicle-specific repair cost - this likely caused systematic over-triggering of total_loss on any claim where non-vehicle costs inflated the reported total. Fixed by wiring real document data into the pipeline for the first time: a new `ClaimsState.claim_documents` field (`src/models/state.py`, defaults to `None`, non-breaking for any claim without parsed document content - which is still every claim submitted through the real API today, since document upload/extraction doesn't exist yet) and `_repair_cost_estimate()` in `damage_assessor.py`, which prefers `claim_documents.repair_estimate.stated_total` and falls back to `estimated_amount` only when no document data is available. Verified by live-testing both few-shot example claims against real Gemini calls before AND after this fix - the "before" run showed the real bug (CLM-STRAT-043 incorrectly came back `total_loss` at a 90% ratio instead of the correct 67.5% `repair` outcome), the "after" run matched expectations exactly on both cases.
- **Intake agent verified live against real data (2026-10-19)**: ran one representative claim from each of the 8 stratified categories through the real `run_intake_agent` with live Gemini calls. All 8 matched expected behavior exactly: clean/fraud_flagged/high_value/missing_document/deductible_exceeds_damage/policy_exclusion all came back `is_valid=True` (correctly NOT pre-judging fraud, deductibles, or exclusions — those are later agents' jobs); `missing_document` correctly named the specific omitted document; `lapsed_policy` (the deliberate 8th category added after this test caught the date bug below) correctly came back `is_valid=False` for the right, specific reason (`policy_active=False`). Injection classifier correctly returned `False` on all 8 (no false positives on ordinary claim narratives). This verified intake's logic only — fraud_crew, damage_assessor, policy_checker, settlement_calculator have NOT yet been run against this dataset.

- **Stratified synthetic claim dataset built from real data** (`src/data/`, generated into `data/stratified_claims/` via `python -m src.data.generate`, not committed-vs-generated decision made yet). 45 claims derived from the real "insurance_claims" CSV (copied into `data/raw/insurance_claims.csv`, SHA-256 verified byte-identical to casefile's copy), scoped to `auto_collision` only, across 7 categories: 20 clean, 10 fraud-flagged (real `fraud_reported=Y` rows), 4 high-value-clean + 2 high-value-fraud (amount >= the calibrated $84,100 threshold), 5 missing-document, 2 deductible-exceeds-damage, 2 policy-exclusion. Each claim produces two files: a `ClaimInput`-shaped submission JSON and a structured-document-fields JSON (`src/models/documents.py`'s `AutoCollisionDocuments` — police_report, other_driver_info, repair_estimate; **photos stays on hold**, not modeled). A new seeded test policy, `POL-AUTO-HIGHDED-US` ($15,000 deductible), was added specifically because the real dataset has no row small enough for a normal deductible to exceed (smallest real `vehicle_claim` is $12,720) — deliberately synthetic on the deductible side, real on the damage side, documented inline in `src/data/selection.py` and `scripts/seed_policies.py`.
- **HITL amount threshold and auto_collision fraud baseline recalibrated against real data, not guessed.** Analyzed the real "insurance_claims" dataset (822 US auto-collision rows from the same Mendeley/Kaggle CSV casefile uses) and found: (1) claim amount does NOT predict fraud in this population — fraud-reported claims (median $63,580) and clean claims (median $61,650) have nearly identical amounts, so the old `hitl.triggers.min_amount=$10,000` would fire on every claim (dataset minimum is $18,000) and had zero discriminating power; (2) the old `fraud_baselines.auto_collision` (avg $6,500, max_normal $25,000) was off by ~10x — 100% of real claims exceeded max_normal, so the anomaly-detection tool would flag every claim regardless of actual risk. Recalibrated: `hitl.triggers.min_amount` is now $84,100 (90th percentile of real claim amounts), reframed as "unusually large for this population, worth a second look" rather than a fraud signal — amount genuinely isn't one here. `fraud_baselines.auto_collision` is now `avg_amount=$63,000, std_dev=$16,000, max_normal=$95,000` (mean + 2 standard deviations of real data). Other claim types' `fraud_baselines` are NOT yet recalibrated — only auto_collision was checked against real data. See project memory `project-smart-claims-dataset-calibration` for the full analysis, including a separate finding (deliberately not acted on): `incident_severity` is a strong real fraud predictor (61% fraud rate for "Major Damage" vs 11-13% for other severities) but isn't a field our `ClaimInput` schema captures at all — flagged as a future opportunity, not added now per explicit user scope decision.
- **Fixed: claimant letters contained the literal text `[CLAIMANT]` instead of the claimant's name.** `src/agents/communication_agent.py`'s prompt told the model to write `[CLAIMANT]` as a placeholder, promising "name will be merged separately" — but nothing ever performed that merge; `comm.message` was persisted and surfaced to the claimant exactly as the LLM wrote it. Fixed with `_merge_claimant_name()`, called right after the LLM responds: substitutes the real name (read from the raw, unmasked claim — the name itself is never put in the prompt, so it never reaches the LLM at all) into both `subject` and `message`. Falls back to "Claimant" if the name is somehow missing. See `tests/test_communication_agent.py`.

## Design principles for this rebuild

Distilled from two unofficial Anthropic architecture-certification study guides (`CCAR-P-Practitioner-Workbook.pdf`, `CCAR-F-Architect-Workbook.pdf`, both in this repo root — informal/unofficial, not Anthropic docs, but the reasoning patterns in them are sound and should govern design decisions here). Apply these as standing judgment calls throughout the rebuild, not just as exam trivia:

- **Model confidence is never a gating signal.** A gate (HITL pause, auto-approve, auto-reject) must be triggered by properties of the action — amount, recipient, blast radius, reversibility — never by the model's self-reported confidence. A confident hallucination scores high exactly where a gate matters most. Confidence may only be used to *sort* an already-triggered review queue (see "Confidence scores" decision above).
- **Least privilege over monitoring.** When a capability isn't needed by a role, remove it — don't grant it and log/alert/confirm instead. Logging and confirmation prompts are detective/compensating controls that observe or interrupt misuse; they don't prevent it.
- **Prompt injection defense = data, not instructions, plus restricted blast radius.** Retrieved/external/user-supplied content is always treated as data the model reads, never as instructions it follows. Pair this with restricting what sensitive actions that content can trigger without human review. Don't rely on trusting the source, a bigger model, or phrase-detection blocklists alone.
- **Structural fixes over prompt wording.** For every failure mode (runaway loops, goal drift, cascading errors, injection-driven actions), the durable fix is a cap, a gate, a contract, a narrowed permission, or a verification step — not a better-worded instruction. A system whose only defense is prompt wording has no defense.
- **Schemas must have a legitimate "I don't know" path.** A required field with no null/unknown option guarantees fabrication when the source is silent. Every extraction schema needs nullable fields, "unknown" enum values, and/or an explicit gaps/not_found array.
- **Schema validity is not correctness.** Schema enforcement guarantees shape, never truth. A perfectly valid record can still contain a fabricated value. Validate semantics separately (range checks, cross-field consistency, sampling against ground truth) — don't treat "it parsed" as "it's correct."
- **Never silently drop a failed/rejected record.** Every validation rejection must be counted and surfaced on a visible metric. A rising rejection rate is often the earliest signal that something upstream changed.
- **Handoffs need an explicit "what I couldn't determine" field.** Between agents/nodes, a conclusion with no provenance, coverage, or uncertainty slot gets treated as verified fact by the receiver. Costs almost nothing to add, prevents a specific, repeatable class of silent failure.
- **Climb the autonomy ladder only as far as the task requires.** Single call → workflow → single agent → multi-agent, in that order. A known, fixed sequence with verifiable success is a workflow, not an agent. Over-engineering (agent where a workflow suffices) is the more common and more tempting mistake.
- **Multi-agent needs one of three specific justifications**: genuine context isolation, real parallelism, or independent verification with a fresh context. "Specialization"/persona alone is not a fourth reason — if every participant shares the same tools and context, it's one agent's job split into theater.
- **Partial failure must be visible, not silently merged.** If a fan-out/batch step has some failures, the output must say so explicitly (partial + what's missing), not quietly present a 7-of-8 result as if it were complete.
- **A human-in-the-loop gate is only real if it has competent reviewers, sufficient information, realistic time, genuine authority to reject, and harness enforcement.** A near-100% approval rate at volume is the diagnostic signature of a gate that has stopped functioning — the fix is to reduce what needs gating (risk-based routing, batching, more reversible-by-default actions), never to loosen the gate itself.
- **Context degradation mid-run is a context problem, not a capability problem.** If a long-running agent starts well and contradicts itself later, diagnose context budget (stale tool results, growing history) before reaching for a bigger model.
